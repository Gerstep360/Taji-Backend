# CU22 · Analizar, clasificar y priorizar incidencias mediante IA

## Comportamiento

T031 conserva los catálogos existentes y agrega Incendios y humo / Personas en
peligro. Los valores activos se envían desde PostgreSQL en cada análisis: una
categoría nueva no requiere cambiar código ni entrenar un modelo. Las categorías
compartidas las administra la cuenta global en `/catalogos-incidencias`; los
administradores de condominio pueden seleccionar y revisar clasificaciones.

Al registrar una incidencia se crea un trabajo `QUEUED` dentro de la misma
transacción. Un trabajador separado reclama trabajos con `SELECT FOR UPDATE
SKIP LOCKED` y consulta NVIDIA. No mantiene una transacción abierta durante la
llamada HTTP, ni carga pesos de modelos en el servidor. Hay un trabajo activo
por incidencia, un límite manual de 12 solicitudes/hora por usuario y 30 segundos
entre análisis del mismo reporte.

La respuesta es una **propuesta**. La categoría y la prioridad oficiales solo
cambian cuando una persona autorizada guarda su revisión. La revisión conserva
la predicción original y registra actor, motivo, fecha, categoría y prioridad.
Se rechazan revisiones duplicadas, propuestas antiguas y reportes que cambiaron.
Si NVIDIA falla, se conserva el error sin credenciales y se habilita clasificación
manual. Reinicios del trabajador recuperan trabajos interrumpidos después de 2 minutos.

## Seguridad y contexto

- La API key permanece en `.env` o `/etc/taji/backend.env`; nunca llega a Web/Móvil.
- Se envía título, descripción y ubicación del reporte, sin datos del reportante;
  se eliminan correos y números personales antes de la llamada.
- Se valida estructura, tamaños, números finitos, catálogos activos y evidencia
  textual. Respuestas inventadas o incompletas pasan a revisión manual.
- Las reglas activas de `RiskRule` comprueban peligros, negaciones y contexto.
  «Hay incendio y los niños están lejos» mantiene el peligro del incendio; mencionar
  niños sin peligro no eleva por sí solo la urgencia.
- Para peligros elevados se muestran acciones seguras del catálogo de reglas.
  La respuesta original del proveedor permanece disponible para auditoría autorizada.
- Una reducción por debajo de las señales requiere confirmación explícita y una
  explicación de al menos 20 caracteres; queda auditada.
- Lectura, solicitud y revisión aplican el alcance de CU19/CU21 y el tenant activo.
  El usuario residente no recibe la predicción original completa ni permisos de revisión.

## Configuración

`config/nvidia.py` lee la configuración NVIDIA del `.env` raíz, Backend/.env y
`/etc/taji/backend.env`; las variables del proceso tienen prioridad. No mezcla
DATABASE_URL ni otras configuraciones del `.env` raíz con los settings Django.

```dotenv
NVIDIA_API_KEY=<configurar fuera de Git>
NVIDIA_MODEL=nvidia/nemotron-3.5-lightning-30b-a3b
NVIDIA_BASE_URL=https://integrate.api.nvidia.com/v1
NVIDIA_ENABLED=True
NVIDIA_AUTO_ANALYZE=True
NVIDIA_TIMEOUT_SECONDS=30
NVIDIA_MAX_TOKENS=1600
```

Se verificó que el modelo Super configurado inicialmente devolvía 404 con esta
cuenta. Lightning respondió correctamente y quedó seleccionado explícitamente en
Backend/.env. Se desactiva razonamiento extendido mediante
`chat_template_kwargs.enable_thinking=false` para reducir latencia y tokens.

En local, ejecutar la API y, en otra terminal de Backend, `./iniciar_ia.ps1`.
También se puede ejecutar `python manage.py run_incident_ai_worker`; `--once`
procesa un único trabajo. La cola necesita que las migraciones estén aplicadas.

## Contratos

Rutas relativas a `/api/v1/paquete3/` (también existen bajo `/api/v1/`):

| Método y ruta | Resultado |
| --- | --- |
| GET `incidents/{code}/ai/` | Últimos cinco análisis y capacidades del actor |
| POST `incidents/{code}/ai/` | Encolar análisis, 202; idempotente si ya hay uno activo |
| POST `incidents/{code}/ai/{id}/review/` | Revisar con category, priority, reason, safety_override |
| GET `incident-ai/catalogs/` | Categorías y prioridades activas |
| POST `incident-ai/catalogs/{categories|priorities}/` | Crear valor; solo administrador global |
| PATCH `incident-ai/catalogs/{kind}/{id}/` | Editar/desactivar sin eliminar referencias históricas |
| GET `incident-ai/metrics/` | Métricas de los últimos 30 días del condominio |

Errores del proveedor: not_configured, timeout, connection_error, rate_limited,
authentication_failed, model_unavailable, provider_unavailable, provider_rejected,
invalid_response, incomplete_response, response_too_large. Nunca se devuelve el
contenido de errores que pudiera incluir datos de autenticación.

Web incorpora un componente reutilizable dentro del detalle CU21 y el acceso
`/analisis-incidencias`. El formulario conserva el motivo si falla el guardado.
Flutter incorpora categoría, prioridad, riesgos con contexto y recomendaciones;
el sondeo está acotado y se cancela al salir de la pantalla.

## Pruebas y despliegue

- Pruebas PostgreSQL de CU18–CU22, incluyendo concurrencia CU21 y la cola integrada.
- Resultado: 107 pruebas del módulo de incidencias, 106 aprobadas y una omitida
  heredada; las 16 pruebas específicas CU22 también aprobaron por separado.
- Pruebas unitarias NVIDIA mediante HTTP simulado: 401/403/404/429/500, timeout,
  desconexión, JSON inválido/truncado/excesivo, datos inventados y validación de contexto.
- Prueba visual Web de propuesta, corrección y fallo/manual a 1440 y 390 px.
- Pruebas Flutter de contrato, decimales, contexto, estado fallido y vista estrecha.
- `probe_incident_ai --samples 3` realiza tres solicitudes reales con reportes
  sintéticos y mide p50/p95. `CU22.nvidia-local.json` guarda el resultado local;
  `CU22.vps.json` registra la verificación de producción. Son muestras funcionales,
  no una estimación de disponibilidad a largo plazo.

Verificación del VPS publicada en `CU22.vps.json`: tres solicitudes correctas,
p50 2.376 s y p95 2.382 s; trabajador alrededor de 76 MiB en reposo. La prueba
integrada `CU22.runtime-vps.json` verificó encolado, procesamiento real, persistencia
y consulta HTTP autorizada (200): 3.703 s de extremo a extremo, con 1.874 s de
análisis. Las consultas de salud internas tardaron entre 4 y 20 ms. Se eliminaron
los registros sintéticos al terminar; se conserva su auditoría técnica sin datos
personales. Estas cifras describen estas muestras, no un SLA ni una prueba de carga.

Web: 107 pruebas unitarias, dos recorridos Playwright CU21/CU22 y build correctos.
Flutter: siete pruebas enfocadas CU21/CU22, análisis estático sin problemas y APK
debug generado. Permanece un fallo anterior ajeno a CU22 en la suite completa
de `access_event_test.dart` (texto «Denegado» duplicado).
El OpenAPI incluido se genera exclusivamente con el URLConf de CU22 y valida
sin errores; no modifica errores de documentación preexistentes de otros módulos.

`deploy/cu22_release.py` prepara releases separadas de Backend/Web, realiza un
respaldo verificado de PostgreSQL antes de migrar y conserva las releases anteriores.
La key se transmite por SFTP a backend.env con permisos 0640, nunca por argumentos.
`deploy/taji-incident-ai.service` limita el trabajador a 384 MiB y media CPU.
La revisión de salud y tres llamadas NVIDIA verifican la publicación. Si falla,
se restauran punteros de release y configuración anterior; las migraciones son aditivas.

Fuentes oficiales: [NVIDIA LLM APIs](https://docs.api.nvidia.com/nim/reference/llm-apis),
[controles de razonamiento Nemotron](https://docs.nvidia.com/nim/large-language-models/2.0.4/turbo/get-started-nemotron-3-super-120b-a12b.html).
