## Integración

Gerstep incorpora origin/Eunice `fbaee2e`, que contiene origin/NoeliaC
`f3843fa`. El registro CU18 y el seguimiento CU19 comparten ahora un único
router: antes el router de seguimiento ocultaba el POST de registro y los
catálogos. Los contratos existentes se conservan bajo `/api/v1/incidents/`
y `/api/v1/paquete3/incidents/`.

## Funcionalidad

- T034: registro inicial y cambios de estado con autor, fecha y motivo.
  La migración 0006 agrega una referencia explícita al estado actual de los
  registros sin historial; no inventa eventos pasados.
- T036: transiciones de CU19 validadas en servidor, con bloqueo de fila dentro
  de la transacción. Requieren permiso y responsable para asignar/iniciar.
  Reabrir elimina las fechas de resolución/cierre. Resolver, cerrar o cancelar
  termina la asignación vigente; reabrir conserva al responsable y abre otro tramo.
- T037: comentarios públicos e internos; el servidor filtra los internos y
  rechaza su publicación/consulta sin autorización.
- T038: fecha objetivo y filtros de pendientes, vencidas, resueltas y a tiempo.
  Los filtros booleanos ausentes no se interpretan como `false`.
- T047: consulta de alertas limitada al condominio y al alcance del usuario.
  Incluye mantenimientos activos próximos (7 días) y vencidos, además de
  incidencias atrasadas. Máximo 100 entradas por tipo y consulta.
- T092: Web `/incidencias`, detalle, historial, evidencias, conversación,
  asignaciones y fecha objetivo. Conserva el comentario escrito si falla el envío.
- T116: Flutter `/incidencias`, listado paginado, filtros, estado, responsable,
  fecha objetivo y línea de tiempo; reutiliza cliente HTTP y sesión segura.
- T127: pruebas heredadas de CU18/CU19 y regresiones de CU21 sobre aislamiento,
  auditoría, transiciones, reapertura, asignaciones y alertas idempotentes.

## Endpoints adicionales

Todos usan sesión autenticada y el alcance del tenant activo.

| Método y ruta (relativa a incidents/) | Resultado |
| --- | --- |
| GET `alerts/` | Alertas visibles sin generar escrituras |
| GET `assignees/` | Personal activo del condominio; solo administración |
| GET `{public_code}/transitions/` | Estados siguientes permitidos para el actor |
| POST `{public_code}/assign/` | `{staff_id, reason?}`; finaliza asignación anterior |
| GET `{public_code}/attachments/{attachment_id}/download/` | Descarga de evidencia con autorización |

Las rutas de CU19 `history/`, `change-status/`, `comments/`, `set-target-date/`
y `attachments/` se mantienen. Las mutaciones de atención generan auditoría
usando la firma real de `record_audit_event`.

## Alertas programadas

Ejecutar desde Backend con el Python del entorno configurado:

```powershell
python manage.py generate_attention_alerts
```

Programar cada 5–15 minutos con un único trabajador (cron o Programador de tareas).
La repetición no duplica alertas para el mismo usuario, recurso, vencimiento y tipo.
Se guardan en `Notification`; este CU no configura correo ni push externo.
No necesita Redis, Celery ni un proceso de sondeo por cliente.

## Verificación y entorno

El entorno `.venv` original apunta a Python 3.11 que ya no está instalado.
Se creó `.venv-cu21` aislado para verificar con Python 3.12 y dependencias del
proyecto. El servicio habitual de PostgreSQL 18 está detenido y Windows no permite
iniciarlo desde esta sesión. Se verificaron las migraciones y las pruebas de
incidencias en una instancia PostgreSQL 18 temporal en `127.0.0.1:55432`,
incluyendo generación concurrente de códigos y transiciones concurrentes.
La instancia se apagó al terminar. No se modificaron credenciales ni datos de producción.

Resultado: 206 pruebas backend en PostgreSQL (una omisión heredada), incluyendo
CU18–CU21, personal CU07, turnos CU13, reportes y tenancy. OpenAPI de incidencias
validado sin errores; conserva dos advertencias por nombres de enums compartidos.
Web: 107 pruebas unitarias y prueba visual CU21 aprobadas; build correcto.
Flutter: analizador sin observaciones, pruebas de contrato CU21 aprobadas y APK debug compilado.

La prueba visual `Frontend/e2e/cu21.spec.ts` usa respuestas controladas para
comprobar interacción y errores a 1440 y 390 px; las reglas de negocio se prueban
por separado contra PostgreSQL. Las capturas están en `Frontend/docs/screenshots/`.
Flutter incluye pruebas de parsing, paginación, filtros y respuestas inválidas.
La suite móvil general tiene un fallo previo en `access_event_test.dart:361`
porque espera una sola aparición de «Denegado», pero el componente la muestra dos veces.

CU22/NVIDIA queda separado: aquí no se usa la clave del `.env` ni se consume su API.
